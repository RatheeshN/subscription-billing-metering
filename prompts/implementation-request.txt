## Architecture

Use a clean Repository Pattern with clear separation of concerns.

Follow approximately this structure:

app/
├── Actions/
├── DTOs/
├── Enums/
├── Exceptions/
├── Http/
│   ├── Controllers/
│   ├── Requests/
│   └── Resources/
├── Jobs/
├── Models/
├── Repositories/
│   ├── Contracts/
│   └── Eloquent/
├── Services/
├── Support/
└── Providers/

Controllers must remain thin.

Responsibilities:

Controller:
- validate/request orchestration
- call Action or Service
- return API Resource/JSON response

Action:
- coordinate a single application use case

Service:
- business logic, especially billing, aggregation, proration, and dashboard calculations

Repository:
- database access and optimized queries

DTO:
- typed data transfer between layers

Job:
- asynchronous/chunked processing

Do not put business logic or large database queries inside controllers.

## Repository Pattern

Create contracts such as:

SubscriptionRepositoryInterface
UsageEventRepositoryInterface
UsageAggregateRepositoryInterface
InvoiceRepositoryInterface

Then create Eloquent implementations.

Example:

Repositories/Contracts/UsageEventRepositoryInterface.php
Repositories/Eloquent/EloquentUsageEventRepository.php

Bind interfaces to implementations in a Service Provider.

Repositories should expose meaningful domain/query operations instead of simply wrapping every Eloquent method.

Bad:

repository->find()

Prefer operations representing actual needs, for example:

getCustomerCycleUsage(...)

Avoid creating unnecessary abstraction purely for the sake of Repository Pattern.

## Subscription Plan Changes

This is a critical requirement.

A customer may upgrade or downgrade during a billing cycle.

Usage before the plan change must be charged using the original plan.

Usage after the change must use the new plan.

Model subscription pricing as effective-dated segments/history rather than simply overwriting subscription.plan_id.

For example:

subscription_segments

- id
- subscription_id
- plan_id
- starts_at
- ends_at
- timestamps

A plan change closes the current segment and opens another segment.

Historical pricing must remain reproducible.

Consider snapshotting billing-relevant plan values into the subscription segment so later edits to a Plan do not retroactively alter historical invoices.

Explain the chosen approach in README.

## Usage Aggregation

Create a queued Job for aggregating usage.

Example:

AggregateDailyUsageJob

Requirements:

- process records in chunks
- avoid loading large datasets into memory
- idempotent/re-runnable
- safely upsert daily aggregates
- handle retries
- appropriate indexes
- explain chunk size choice

Create a daily_usage_aggregates table.

Suggested uniqueness:

merchant_id + customer_id + usage_date + subscription_segment_id

This allows usage to remain associated with the pricing segment that applies at the time it occurred.

## Billing

Create a BillingService.

Billing must calculate:

base price
+
overage charges
=
invoice total

Implement:

included allowance
overage usage
overage rate
proration
mid-cycle subscription start
mid-cycle upgrade
mid-cycle downgrade
multiple pricing segments in one billing cycle

For each effective subscription segment:

1. determine segment duration within billing cycle
2. calculate prorated base price
3. calculate the segment's prorated included allowance according to a clearly documented rule
4. determine usage belonging to that segment
5. calculate overage
6. calculate overage charge
7. create invoice line(s)

Use a deterministic proration strategy based on time/days and document the exact rule.

Clearly define boundary semantics such as:

starts_at inclusive
ends_at exclusive

Avoid double-counting usage exactly at a plan-change boundary.

Invoice generation must be safe to retry without creating duplicate invoices.

Use database uniqueness and transactions where appropriate.
